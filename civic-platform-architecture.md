# 1. EXECUTIVE SUMMARY

## 1.1 Platform Overview

Najia Community Bridge is a civic technology platform designed to strengthen the relationship between Nigerian citizens and their government while providing access to legal resources and verified evidence management. The platform operates on three interconnected pillars: citizen engagement with governance, evidence integrity and verification, and access to legal representation.

The platform serves as a non-binding, transparent bridge between citizens and institutions, enabling structured feedback on government policies, confidence measurement in elected officials, secure evidence handling for disputes, and connection to qualified legal professionals. All activities are conducted within clear legal and ethical boundaries, with robust safeguards against manipulation, misuse, and misinterpretation.

## 1.2 Core Mission

To empower Nigerian citizens with tools for informed civic participation, verified evidence management, and access to justice, while maintaining the highest standards of integrity, transparency, and legal compliance.

## 1.3 Value Proposition

| Stakeholder | Value Provided |
|-------------|----------------|
| Citizens | Voice in governance, evidence security, legal access, civic education |
| Government | Real-time citizen sentiment data, structured feedback, reduced distrust |
| Legal Professionals | Client acquisition, pro bono opportunities, professional visibility |
| Civil Society | Data for advocacy, citizen engagement tools, accountability monitoring |
| Investors/Donors | Social impact, measurable outcomes, sustainable model |

| Risk | Mitigation |
|------|------------|

| Risk | Mitigation |
|------|------------|
| Voter manipulation | Government ID verification; one vote per person per poll |
| Bot attacks | CAPTCHA on voting; rate limiting; IP monitoring |
| Vote buying/selling | Individual vote verification; no financial incentives for voting |
| Reputation manipulation | **No reputation weighting on civic votes** - strict one-person-one-vote |

| Risk | Mitigation |
|------|------------|
| Social polarization | Results shown with confidence intervals; avoid ranking leaders |
| Harassment of officials | Focus on policy, not personal attacks; moderation of comments |

| Echo chambers | Show diverse perspectives; present context and background |

# 4. EVIDENCE INTEGRITY & DEEPFAKE DETECTION

## 4.1 Overview

The evidence integrity system addresses two distinct but complementary concerns:
1. **Chain-of-custody integrity** - ensuring uploaded files remain untampered
2. **AI-manipulation detection** - identifying synthetically generated or altered media

These are handled separately because they serve different purposes, use different technologies, and carry different implications for users.

---

## 4.2 Evidence Integrity Pipeline

### 4.2.1 Purpose
Guarantee that uploaded evidence has not been silently altered after upload, maintaining a verifiable chain of custody.

### 4.2.2 Method
| Step | Description |
|------|-------------|
| Upload | User uploads evidence file through web or mobile app |
| Hash Generation | SHA-256 cryptographic hash computed from the file |
| Timestamp | Append-only timestamp record created |
| Storage | File stored securely with hash and metadata |
| Verification | Re-hash and compare on every access |
| Audit Trail | All access events logged |

### 4.2.3 Scope
All evidence types are covered:
- Images (JPG, PNG, WebP)
- Video (MP4, AVI, WebM)
- Audio (MP3, WAV, M4A)
- Documents (PDF, DOCX, TXT)

### 4.2.4 Verification Display
| Indicator | Description |
|-----------|-------------|
| Green Badge | Verified: File matches original upload |
| Red Warning | Verified: File has been altered |
| Pending | Verification in progress |
| Not Applicable | File type doesn't support hash verification |

---

## 4.3 AI-Powered Manipulation Detection

### 4.3.1 Purpose
Flag plausible AI-generated or manipulated media as an input to human review, not as a definitive verdict.

### 4.3.2 Scope
| Media Type | Detection Applied | Notes |
|------------|-------------------|-------|
| Images | Yes | Primary detection focus |
| Videos | Yes | Multiple detection methods combined |
| Audio Only | No | Audio deepfakes in scope, but initially skipped due to complexity |
| Documents | No | Manipulation assessed through hash only |

### 4.3.3 Detection Methods
| Method | Description | Applicable Media |
|--------|-------------|------------------|
| Metadata Analysis | Examine file metadata for generation artifacts | Images, Videos |
| Visual Artifact Detection | Detect pixel-level anomalies, compression patterns | Images |
| Audio-Video Sync Analysis | Check lip sync and audio coherence | Videos |
| Facial Inconsistency Detection | Identify inconsistent facial features, blending artifacts | Images, Videos |
| Generation Watermarks | Detect generation-time watermarks (limited coverage) | Images, Videos |

### 4.3.4 Detection Output
| Output Type | Description |
|-------------|-------------|
| Confidence Score | Float value indicating likelihood of manipulation |
| Category | Low (0-33%), Medium (34-66%), High (67-100%) |
| Detection Model Version | Which model and thresholds scored this file |
| Applicability Flag | Whether AI detection was attempted for this file type |

### 4.3.5 Display to Users
| Display Element | Description |
|-----------------|-------------|
| Integrity Status | "This file passed/failed integrity checks" |
| AI Detection Status | "This file was/was not flagged for AI manipulation" |
| User Guidance | "Users should independently evaluate authenticity" |
| Confidence Level | Low / Medium / High (with explanatory text) |
| Disclaimer | "This is an automated detection, not a definitive verdict" |

### 4.3.6 Human Review Process
| Step | Description |
|------|-------------|
| Auto-Flag | High-confidence detections automatically flagged |
| Moderator Review | Flagged content reviewed by trained moderators |
| Escalation | Ambiguous cases escalated to specialized reviewers |
| User Appeal | User can request human re-review |
| Final Status | Status updated based on human review |

### 4.3.7 Known Limitations
| Limitation | Communication |
|------------|---------------|
| Detectors tuned for synthetic faces/deepfakes | Most civil-dispute evidence (property damage, receipts, chat screenshots) is not in-scope |
| False positives possible | Users are informed of detection limitations |
| False negatives possible | Users are encouraged to independently verify |
| No detection is perfect | Clear communication of probabilistic nature |
| Coverage limited to certain media types | Audio, documents, and some image formats may not be analyzed |

---

## 4.4 Detection Pipeline Flow

| Stage | Process |
|-------|---------|
| 1 | User uploads evidence |
| 2 | Hash + Timestamp generated (integrity) |
| 3 | File type checked |
| 4a | If not image/video: Skip AI detection; integrity-only verification |
| 4b | If image/video: Proceed to AI detection |
| 5 | Metadata analysis performed |
| 6 | Visual artifact detection performed |
| 7 | Audio-video sync analysis performed (video only) |
| 8 | Ensemble score calculated |
| 9 | Category assigned: Low (green), Medium (yellow, flagged), High (red, moderator required) |
| 10 | Results stored and displayed |

# 6. TECHNICAL ARCHITECTURE

## 6.1 Architecture Overview

The platform is built as a single deployable service with two entry points sharing one service layer. This ensures business logic is not duplicated and the web application experiences no unnecessary network hops.

### 6.1.1 Architecture Components

| Component | Description |
|-----------|-------------|
| **Web Application** | Full-stack web framework with file-based routing, server-side rendering, and server functions for mutations and data loading |
| **API Layer** | Lightweight JSON API mounted within the web server, serving mobile applications, webhooks, and third-party integrations |
| **Services Layer** | All business logic resides here - the single source of truth imported by both web actions and API routes |
| **Database Layer** | Relational database with ORM for type-safe queries |
| **Cache/Session Layer** | Lightweight database for sessions, rate limiting, and caching |
| **File Storage** | Content delivery network for media delivery |
| **Authentication** | JWT-based with session store |

### 6.1.2 Request Flow

| Path | Process |
|------|---------|
| Web Browser Request | Loads from server → Server-side rendering → Web app page |
| Web Mutation | Server function called → Services layer → Database |
| Mobile App Request | HTTP request to API layer → Services layer → Database |
| Webhook Request | HTTP request to API layer → Services layer → Database |
| Third-Party Integration | HTTP request to API layer → Services layer → Database |

### 6.1.3 Architecture Principles
- **Single Source of Truth:** Business logic lives only in the services layer
- **Thin Entry Points:** Web actions and API routes only handle validation, authentication, and shaping responses
- **Direct Calls:** Web app calls services directly in-process, no HTTP hop
- **Shared Validation:** Validation schemas are shared across all entry points
- **No Reverse Dependencies:** Services never import from web actions or API routes

## 6.4 Database Design

### 6.4.1 Key Tables

| Table | Description |
|-------|-------------|
| **users** | Platform user accounts, verification status |
| **jurisdictions** | Normalized location data (national, state, local) |
| **cases** | Civil dispute cases with consent-based participation |
| **evidence** | Uploaded evidence with hash and AI detection results |
| **poll_questions** | Questions for policy and confidence polls |
| **policy_polls** | Policy sentiment poll metadata |
| **policy_votes** | Citizen votes on policy polls |
| **officials** | Elected officials for confidence voting |
| **confidence_votes** | Citizen confidence votes on officials |
| **lawyers** | Verified lawyers with practice information |
| **votes** | Structured voting within cases/mediation |
| **moderation_actions** | Moderator actions on content |
| **appeals** | User appeals of moderation decisions |

### 6.4.2 Design Principles

- **Normalization:** Avoids repeated free-text fields; uses foreign keys to lookup tables
- **Immutable Records:** Append-only for sensitive actions; no deletes
- **Versioning:** Models and thresholds are versioned for reproducibility
- **Uniqueness:** Database-level unique constraints prevent duplicate voting
- **Auditability:** All changes tracked with timestamps and user IDs
- **Partitioning:** Large tables (votes, evidence) partitioned by date from the start

### 6.4.3 Key Data Relationships

- Cases belong to a jurisdiction (normalized)
- Evidence belongs to a case and uploader
- Policy votes unique per poll per voter
- Confidence votes unique per official per voter per quarter
- Lawyers are users with additional professional information
- Officials are normalized entities with jurisdiction and term information

## 6.6 Security Architecture

### 6.6.1 Authentication Flow

| Step | Process |
|------|---------|
| 1 | User registers with email/phone |
| 2 | Email/phone verification sent |
| 3 | User completes verification |
| 4 | Identity verification initiated (Jumio/Onfido) |
| 5 | User receives JWT token |
| 6 | JWT stored in secure HTTP-only cookie (web) or secure storage (mobile) |
| 7 | JWT validated on each request |
| 8 | Session tracked in SQLite |
| 9 | Session expires after inactivity |

### 6.6.2 Authorization Layers

| Layer | Access Control |
|-------|----------------|
| API Layer | JWT verification, role-based access |
| Services Layer | Business logic authorization |
| Database Layer | Row-level security |
| File Storage | Signed URLs, time-limited access |

### 6.6.3 Data Protection

| Element | Protection |
|---------|------------|
| Government IDs | Hashed, not stored as plaintext |
| User Data | Encrypted at rest and in transit |
| Evidence Files | Encrypted at rest; access logged |
| Votes | Anonymous in results; stored with user ID for uniqueness |
| Legal Data | Access restricted to involved parties |
| Session Data | Stored in SQLite with TTL |

### 6.6.4 Security Controls

| Control | Implementation |
|---------|----------------|
| Rate Limiting | SQLite-backed, per user/IP |
| Input Validation | Zod schemas on all entry points |
| CSRF Protection | SameSite cookies, CSRF tokens |
| XSS Prevention | Content Security Policy, sanitization |

# 7. MODERATION & CONTENT GOVERNANCE

## 7.1 Moderation Overview

The platform maintains content integrity through a multi-tiered moderation system that combines automated detection with human review.

### 7.1.1 Moderation Principles
- **Transparency:** All moderation actions are documented and visible to affected users
- **Appeal:** Users can appeal moderation decisions
- **Consistency:** Clear guidelines applied uniformly
- **Proportionality:** Actions match severity of violations
- **Human Review:** Automated actions are reviewed by humans

---
